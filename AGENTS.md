# Agent Instructions

These instructions apply to this repository: lib-yahboom-gamepad, a published
Wendoo LIBRARY -- an ordinary Wendoo project consumed as a dependency
by other projects. Its identity is its `<owner>/<repo>` coordinate,
`wendoo-lang/lib-yahboom-gamepad`. Consuming applications list it in a curated
catalog and install it at a pinned commit, so what ships from this
repository is exactly what was published and reviewed.

Before working anywhere in this repository, read
`.github/instructions/global.instructions.md` (comment guidelines, the
ASCII-only rule, deletion discipline, the broad-view rule) and
`.github/instructions/agent-posture.instructions.md` (working
temperament, the tile-language tenets, and the documentation
contract).

## Git Is Read-Only

Git is a read-only tool for every agent working here. Inspect freely:
`status`, `log`, `diff`, `show`, `blame`, and the like. `git rm` and
`git mv` are allowed as ordinary file operations while editing.

Everything that changes repository state -- the working tree's history,
the index, commits, tags, branches, pushes -- is the user's to run.
PUBLISHING IS THE USER'S ACT: the `wendoo publish` command bumps the
manifest version, commits, tags `v<version>`, and pushes. Never run
it, never bump the manifest `version` field, and never edit the
manifest `identity` field -- identity is stamped by publish tooling,
never hand-authored.

## Repo Shape (what is authored, what is generated)

- `wendoo.json` is the manifest and the single source of truth for
  what the library comprises. Its `files` list is authoritative:
  adding a source, doc, or icon file to the library MEANS listing it
  there, and a listed file must exist. Its `extensions` field is the
  dependency list (the manifest field keeps that historical name;
  the concept is libraries).
- `*.ts` at the root are the library's tiles and modules. The entry
  module (`index.ts`, where present) defines the published symbol
  surface.
- `docs/` holds one markdown page per documented tile, paired with
  the tile's `docs:` reference. `icons/` likewise for `icon:`.
- `.libraries/` is the INSTALLED dependency tree: read-only,
  regenerated from the manifest. Never edit anything under it.
- `tsconfig.json` is GENERATED by Wendoo tooling and overwritten on
  project open; never edit it.

## The TypeScript Environment (not a default setup)

This library's TypeScript is compiled by the Wendoo toolchain, not a
project-local tsc, and its typings come from the platform, not from
npm:

- Types are AMBIENT, supplied from the core package and the declared
  target's device API when Wendoo tooling opens or compiles the
  project. `import ... from "wendoo"` (Context, System, the
  Sensor/Actuator/Conversion factories, Buffer) and
  `import ... from "@lib/<owner>/<repo>"` (installed dependencies)
  are the only import roots. There are no node builtins, no DOM, and
  no @types packages -- `Buffer` here is Wendoo's, not node's.
- Code executes as Wendoo VM bytecode inside the sandbox, under the
  VM's budgets and host-call surface. Host access goes through the
  Context (`ctx.microbit.*` on this target); there is no other
  runtime.
- The generated `tsconfig.json` wires `@lib/*` to `.libraries/`;
  both it and the installed tree are regenerated by tooling. Never
  add npm packages, @types, or compiler configuration to make
  editor errors go away -- a type the code cannot see comes from a
  missing dependency in the manifest's `extensions` field or from
  tooling that has not regenerated, not from a setup step this
  repository is missing.

## Validation

This repository carries no build or test tooling of its own -- no
package.json, no scripts. Changes are validated by the consuming
applications (the owner installs the library into an app and runs
its fixtures and playtests). After editing: run `git diff --check`,
state plainly what behavior changed, and name what the owner should
verify in a consuming app. Never claim a change is verified here.

## Code Quality

- Complete implementations only: no TODO, FIXME, stub bodies, or
  placeholder code.
- Write type-only imports as top-level `import type` statements.
- Build the minimum the task needs; the burden of proof is on
  inclusion. A field, guard, or abstraction earns its place by a
  failure mode possible today.
